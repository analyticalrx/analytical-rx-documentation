Canonical Event Table Dictionary

Field-level explanation, ER diagram, and access restrictions for the MVP database that stores PrimeRx webhook events in canonical format.

Current Scope

This schema stops at the current implementation goal: receive webhook events, store processing/audit records, save a PHI-minimized canonical event, and allow the API enrichment worker to update missing safe fields later.

This is not the full analytics warehouse design. It does not define forecasting tables, feature marts, dashboard-specific aggregates, or long-term patient analytics.

Data Flow

  1. Webhook receiver receives the PrimeRx event and creates an audit record.
  2. Receiver optionally stores the raw payload in restricted storage and saves only the storage pointer in the database.
  3. Processor reads the queued event, validates it, de-duplicates it, and stores restricted source identifiers if present.
  4. Processor creates one canonical PHI-minimized event row.
  5. API enrichment worker uses restricted RxNo, RefillNo, and pharmacy reference to fetch missing details and update only safe canonical columns.

Access Summary

Actor or service Allowed access Restriction
Webhook receiver Lambda Insert into ops.webhook_event_audit. Insert into ops.raw_payload_archive only if raw archive is enabled. Should not write to canonical analytics tables directly. Should not log raw payload content.
Webhook processor Lambda Read/update audit rows, upsert restricted source reference rows, insert canonical event rows. May handle raw payload during processing, but must not copy direct patient identifiers into canonical tables or logs.
API enrichment worker Read ops.source_prescription_reference_restricted. Update safe missing fields on analytics.canonical_pharmacy_event. Update audit/enrichment status. Should not expose real RxNo, RefillNo, or raw API responses outside the restricted service boundary.
Dashboard/API application Read analytics.canonical_pharmacy_event and safe core pharmacy/tenant labels for authorized tenant/pharmacy only. No direct access to ops schema or raw payload archive.
Database administrator Manage schema, indexes, migrations, database roles, backups, and emergency support. Access should be limited to named admin users. Production access should be audited.

Restrictions To Enforce

Place Restriction Reason
API Gateway / receiver Lambda Authenticate the webhook request before accepting it. Prevents unauthenticated event injection.
SQS message Keep messages encrypted. Do not add extra debug fields containing patient identifiers. Queue messages may contain source payload data during MVP processing.
CloudWatch logs Log metadata only: request ID, event type, tenant, pharmacy, status, and error code. Do not log raw payloads. Logs are easy to over-share and should not become a PHI store.
ops.raw_payload_archive Store pointer and hash only. Raw JSON belongs in restricted encrypted object storage if retained. Keeps the database from becoming a raw PHI payload store.
ops.source_prescription_reference_restricted Backend services only. Contains real RxNo and RefillNo. These identifiers are required for PrimeRx API lookup, but should not appear in dashboards.
analytics.canonical_pharmacy_event No patient name, DOB, address, phone, email, insurance member ID, prescription notes, or raw RxNo. This is the safe table used by product dashboards and basic reporting.
Database access Use separate roles for receiver, processor, API enrichment, dashboard app, and admin. Apply tenant filtering for app reads. Limits blast radius and prevents dashboard users from reaching restricted source identifiers.

API Enrichment Update Rules

  • API enrichment should use restricted source references only from ops.source_prescription_reference_restricted.
  • API enrichment may update missing safe fields in analytics.canonical_pharmacy_event, such as drug, payer, status, and payment amounts.
  • API enrichment must not write patient names, DOB, address, phone, email, insurance member ID, notes, images, raw RxNo, or raw RefillNo into canonical tables.
  • If enrichment fails, update enrichment_status and the audit failure fields without logging raw API response payloads.
