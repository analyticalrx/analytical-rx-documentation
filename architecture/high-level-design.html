High-Level Design for Multi-Pharmacy Analytics Platform

Purpose

This document defines the target architecture for the Multi-Pharmacy Analytics Platform before all source-system details are available. The design is based on the requirements brief, the PrimeRx API Swagger spec, and the PrimeRx webhook onboarding guide.

The product should be designed as a pharmacy analytics and operations platform first, with SaaS-ready boundaries from the start.

Confirmed Source Facts

  • PrimeRx exposes a documented API at https://gatewayapi.micromerchantsystems.com/swagger/index.html
  • The API spec is PrimeAPI Docs (MMS.GatewayApi) version v3.6.1
  • The API uses Bearer authentication
  • PrimeRx also supports webhooks for near-real-time event notifications
  • The webhook guide states that webhook events are HTTPS POSTs with JSON payloads
  • Both the API and the webhook payloads include PHI-heavy fields, so the analytics layer must treat raw source data as restricted until transformed
  • We do not yet know whether PrimeRx provides a bulk historical export, batch send, or other backfill mechanism, so that remains a key vendor question

Design Principles

  1. Canonical model first, source adapters second.
  2. Webhooks are for near-real-time event triggers, not the only data source.
  3. API pulls are for enrichment, backfill, and reconciliation.
  4. PHI must be suppressed or transformed before data enters the analytics database.
  5. Everything must be tenant-safe from the beginning, even if the first deployment is internal only.
  6. Build the minimum useful slice first, then widen the surface area.

System Layers

1. Source Layer

This layer includes all systems that provide operational data.

  • PrimeRx API
  • PrimeRx webhooks
  • Bulk export or scheduled report send, if available
  • Current Airtable prototype
  • Finance inputs
  • Documents and licenses
  • Tasks and calendar inputs
  • Doctor relationship activity

2. Restricted Ingestion Boundary

This is the highest-risk zone in the architecture. Raw source payloads may contain direct patient identifiers and other PHI, so this layer must be isolated and auditable.

Responsibilities:

  • Authenticate inbound webhook/API traffic
  • Store raw payloads in restricted quarantine storage
  • Validate schema and payload shape
  • Classify fields by policy
  • Suppress, hash, bucket, or drop PHI
  • Emit import and privacy audit logs
  • Route bad payloads to exception handling

3. Canonical Data Model

This is the stable internal model that every source maps into.

Core entities:

  • Store
  • Prescription fill
  • Payer
  • Drug
  • Prescriber
  • Patient cohort or pseudonymous token
  • Employee
  • Task
  • Financial fact
  • Document or license
  • Import job
  • Alert
  • User and permission

4. Analytics and Decision Layer

This layer turns normalized data into business value.

  • KPI calculations
  • Store comparison
  • Payer profitability
  • Drug profitability
  • Root-cause analysis
  • Alerts and exceptions
  • Recommendations
  • Scenario modeling

5. Product Layer

Role-specific interfaces should sit on top of the analytics layer.

  • Owner / executive dashboard
  • Store manager dashboard
  • Technician dashboard
  • Bookkeeper / finance dashboard
  • Compliance / admin dashboard
  • Doctor relations dashboard
  • Strategy / scenario center

6. Platform Services

Shared services needed by all product surfaces.

  • Authentication
  • RBAC
  • Multi-tenant isolation
  • Audit logging
  • Monitoring
  • Secrets management
  • Support/admin tooling
  • Future billing and onboarding

Ingestion Strategy

The recommended integration model is:

WebhooksNear-real-time event trigger
APIDetail lookup, backfill, reconciliation
Bulk / BatchHistorical load if PrimeRx supports it

Important operational rule:

  • Webhooks should ack fast and hand off work asynchronously.
  • API calls should be rate-limited, idempotent, and resumable.
  • Reconciliation must exist even if webhooks are reliable.
  • The system should be able to rebuild KPIs from source data.

PHI Policy

The platform should not ingest direct patient identifiers into the analytics database unless compliance and legal explicitly approve a different policy later.

Preferred handling:

  • Remove patient name, address, DOB, phone, email, driver license, prescription image, and free-text identifier fields
  • Convert DOB into age band or another bucketed form
  • Convert address into ZIP3, city, or market area if needed
  • Use internal row IDs, source transaction IDs, or one-way pseudonymous tokens instead of prescription numbers when possible
  • Treat any webhook or API response as PHI until processed by the restricted ingestion boundary

KPI Scope

The first analytics release should support:

  • RX volume
  • Revenue
  • Gross profit
  • Estimated net profit
  • Average profit per RX
  • Payer mix
  • Drug profitability
  • Rejections and reversals
  • Prescription status and queue movement
  • Doctor referral performance
  • Task completion
  • Compliance expirations
  • Financial close status

Recommended MVP Slice

The first buildable slice should prove the following flow:

1PrimeRx payload
2Restricted intake
3PHI minimization
4Canonical mapping
5KPI calculation
6Dashboards + drilldowns
7Import audit log

Build Sequence

  1. Finalize source questions and assumptions.
  2. Lock the canonical model.
  3. Build the restricted ingestion boundary.
  4. Implement API connector and webhook receiver.
  5. Implement PHI suppression and mapping.
  6. Load the canonical analytics database.
  7. Build owner and store dashboards.
  8. Add alerts, exceptions, and audit views.
  9. Extend to tasks, documents, doctor CRM, and finance workflows.
  10. Add SaaS tenancy, onboarding, and billing.

Key Tradeoffs

API-first vs webhook-first

API-first is required for backfill and reconciliation. Webhooks are the best near-real-time trigger, but they do not eliminate the need for polling or batch sync.

Airtable vs custom backend

Airtable is useful as a prototype reference, but a custom database is the cleaner long-term core if the product is meant to become SaaS.

PHI-minimized vs patient-continuity analytics

Pure aggregate analytics is safer. If continuity is required, a pseudonymous token strategy is preferable to exposing direct identifiers.

Open Questions For PrimeRx

  • Do you provide a bulk API, bulk export, scheduled report send, SFTP export, or other batch mechanism for historical load and reconciliation?
  • Can webhooks and APIs exclude PHI or direct patient identifiers?
  • Can you provide pseudonymous patient tokens if continuity is needed?
  • What fields are available for prescription, payer, drug, prescriber, pharmacy, rejection, reversal, and billing analytics?
  • Are webhook retries, replay, event IDs, and schema versioning available?
  • What is the best supported method for multi-store analytics?

Architecture Summary

The platform should be built as a pipeline that turns operational pharmacy data into explainable business decisions. The main system boundary is not the dashboard. The main boundary is the PHI-controlled ingestion layer that protects the analytics store and makes the rest of the platform safe to scale.
