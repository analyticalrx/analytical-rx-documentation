Canonical Event Database Schema

MVP database design for storing PrimeRx webhook/API events as audit-ready, PHI-minimized canonical records.

Purpose

This document defines the first database schema for the webhook processing pipeline. It gives the processor Lambda a clear destination for processed events without mixing raw PrimeRx payloads, restricted source identifiers, and analytics-facing records.

The core rule: store real RxNo and RefillNo only in restricted operational tables. Dashboards and analytics use prescription_reference_token and fill_reference_token.

Current scope stops at saving webhook data into canonical format, upserting safe drug/payer lookup rows, storing event payment components, and letting the API enrichment worker update safe missing fields. This is not the full reporting warehouse or ML feature model.

MVP Decisions

Decision Recommendation Reason
Database PostgreSQL-compatible database such as RDS PostgreSQL or Aurora PostgreSQL Works well for structured audit, canonical records, and API enrichment updates.
Storage zones ops schema for restricted operational data, analytics schema for PHI-minimized records, core schema for tenant/pharmacy references Prevents accidental mixing of source identifiers and dashboard-facing data.
Raw payload retention Optional restricted S3 archive with DB pointer and payload hash Allows replay/troubleshooting without copying raw PHI into analytics tables.
Source identifiers Store real RxNo and RefillNo in ops.source_prescription_reference_restricted API enrichment needs real vendor identifiers. Tokens alone cannot call PrimeRx.
Canonical model Use one event table plus normalized core.drug, core.payer, and event payment rows Keeps one source of truth for safe drug and payer attributes. Exact original webhook/API values remain available only through restricted raw archive when retention is enabled.
Cash payments Store as payment_type = 'cash' with payer_id = null Cash is not an insurance payer, so it should not create a payer dimension record.

Tables

core.tenant

One row per pharmacy group or customer tenant. Every operational and analytics row must belong to a tenant.

core.pharmacy

One row per store/pharmacy location. Stores source pharmacy IDs, NPI/NCPDP when available, and tenant ownership.

core.drug

Normalized drug lookup rows upserted from webhook/API fields such as NDC, product ID, drug name, strength, form, and manufacturer.

core.payer

Normalized insurance payer lookup rows upserted from payer name, BIN, PCN, and source insurance code when available.

ops.raw_payload_archive

Pointer to restricted raw payload storage, not the raw JSON itself. Stores hash, size, source, and retention metadata.

ops.webhook_event_audit

Lifecycle record for each received event: received, queued, processing, processed, failed, duplicate, or needs enrichment.

ops.source_prescription_reference_restricted

Restricted source lookup table containing real RxNo and RefillNo. Used by backend jobs for API enrichment and reconciliation.

analytics.canonical_pharmacy_event

PHI-minimized event facts used by dashboards, reconciliation, and API enrichment updates.

analytics.canonical_event_payer_payment

Bridge table between canonical events and payers. One row per event payment component: primary insurance, secondary insurance, tertiary insurance, patient pay, cash, or other payment type.

Canonical Event Fields

Field group Columns Notes
Tenant/store tenant_id, pharmacy_id Required on every row. These support tenant isolation, store-level dashboards, and row-level security later.
Lineage audit_event_id, source_system, source_event_type Links each canonical row back to the processing audit record.
Canonical type canonical_event_type Normalized event type such as claim_billed, claim_reversed, or claim_rejected.
Safe continuity prescription_reference_token, fill_reference_token Tokens only. Real source identifiers stay in the restricted ops schema.
Status rx_status, claim_status, fulfillment_status, queue_status Nullable because not every event includes every status.
Drug/payer/prescriber drug_id, prescriber_npi Drug details are read from core.drug. Payer details are reached through analytics.canonical_event_payer_payment to core.payer.
Prescription/fill details days_supply, quantity_ordered, quantity_dispensed, quantity_remaining, date_filled, date_picked_up Safe fill-level facts from webhook/API. Direct patient identifiers remain excluded.
Financial total_amount, ingredient_cost_amount, dispensing_fee_amount, amount_due Event-level Rx/cost facts live on the canonical event. Payer and patient payment amounts live in analytics.canonical_event_payer_payment.
Payment breakdown payment_type, payer_id, payer_sequence, paid_amount Payer is linked through analytics.canonical_event_payer_payment: canonical event ID to payment row, then payment payer_id to core.payer. Cash rows use payment_type = 'cash' and payer_id = null.
Quality enrichment_status, data_quality_status Allows dashboards to distinguish complete rows from partial webhook-only rows.

Token Strategy

The processor should generate stable HMAC tokens using a secret owned by the backend, not a plain SHA hash. Tokens must include tenant and pharmacy context so the same source identifier in two tenants does not produce the same token.

prescription_reference_token = HMAC_SHA256(secret, tenant_id + pharmacy_id + rx_no)
fill_reference_token         = HMAC_SHA256(secret, tenant_id + pharmacy_id + rx_no + refill_no)

Idempotency Strategy

The audit table owns idempotency. The processor should create one canonical row only after the event is accepted as non-duplicate.

  1. Use PrimeRx event ID if PrimeRx provides one.
  2. Otherwise use tenant, pharmacy, source event type, source event timestamp, RxNo, and RefillNo.
  3. If no stable event identity exists, use the receiver request ID and raw payload hash as fallback.

The database enforces unique (tenant_id, source_system, idempotency_key) on ops.webhook_event_audit.

PHI Exclusion Rules

The canonical analytics schema must not store patient first name, patient last name, full DOB, full address, phone number, email, driver license, insurance member ID, prescription images, or free-text notes.

If a field is needed for debugging or API lookup, it belongs in the restricted operational layer, not in analytics.canonical_pharmacy_event.

Access Model

Role Allowed access Not allowed
Webhook processor Write ops.webhook_event_audit, ops.source_prescription_reference_restricted, core.drug, core.payer, analytics.canonical_pharmacy_event, and analytics.canonical_event_payer_payment Logging raw payloads or exposing source identifiers to dashboards
API enrichment worker Read restricted source references, call PrimeRx API, write safe enriched fields back to lookup, canonical, and payment records Writing direct patient identifiers to analytics tables
Dashboard/API application Read analytics records and safe core labels for authorized tenant/pharmacy only Reading ops.source_prescription_reference_restricted or raw payload archive
Data engineer Read canonical records after access approval Using raw PrimeRx payloads or restricted source references as dashboard source tables

For production, tenant filtering should be enforced with database roles and row-level security or an equivalent application-layer control. The MVP schema includes tenant_id and pharmacy_id on every table so that control can be added without changing the model.

Example Processing Write

  1. Receiver writes a metadata audit row with status received and optionally stores raw payload in restricted archive.
  2. Processor validates payload and creates/updates ops.source_prescription_reference_restricted with real RxNo, RefillNo, and tokens.
  3. Processor updates audit status to processing.
  4. Processor suppresses PHI, upserts safe drug/payer lookup rows, and maps safe fields into analytics.canonical_pharmacy_event.
  5. Processor writes event payment rows for insurance, patient pay, cash, or other payment components.
  6. Processor updates audit status to processed, failed, duplicate, or needs_enrichment.

Raw Payload Retention Decision

For MVP, restricted raw payload archive records should default to a 30-day retention window. This gives the team a short replay/debug window without turning raw webhook/API payloads into a long-term product data store.

This is an engineering default for MVP review only. Before production, legal/security should confirm whether 30 days is acceptable, whether any customer agreement changes it, and whether production deletion should be enforced by S3 lifecycle policy, database cleanup job, or both.

Open Questions

  • Does PrimeRx provide a stable webhook event ID?
  • Does every prescription-level event include store/pharmacy identity, RxNo, and RefillNo?
  • Are financial fields reliable in webhooks, or should they be treated as API-enriched fields?
  • Should production enforce the 30-day raw payload retention policy through S3 lifecycle rules, a database cleanup job, or both?
  • When will security approve or reject patient-level pseudonymous continuity for refill/adherence analytics?
