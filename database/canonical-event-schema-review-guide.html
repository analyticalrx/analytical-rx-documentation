Canonical Event Schema Review Guide

Step-by-step review guide for the MVP database schema that stores PrimeRx webhook/API events in a canonical, dashboard-ready format.

How To Review This Document

  1. Start with the scope and phase boundary so the review stays focused on Phase 1.
  2. Review the source-of-truth rules to understand where each type of data belongs.
  3. Review the main tables and relationships.
  4. Review the access model and PHI restrictions.
  5. Use the checklist at the end to leave comments or approval feedback.

This is the main reviewer document. Use the linked field dictionary, SQL, and ERD only when you need column-level or implementation-level detail.

Review Goal

The goal is to confirm that the Phase 1 schema can receive PrimeRx webhook events, store restricted operational references safely, transform events into a PHI-minimized canonical model, and support starter dashboards and API enrichment.

This review is not asking the team to finalize forecasting, long-term analytics marts, doctor CRM workflows, or production security policy. Those will be reviewed separately.

Phase 1 Boundary

Included now Not included now
Webhook/API event audit and idempotency tracking. Forecasting models or machine learning feature marts.
Restricted storage of source prescription identifiers needed for API lookup. Patient-facing CRM or patient outreach workflows.
Normalized drug and payer lookup tables. Long-term analytics warehouse design.
Canonical pharmacy event rows and payment rows for starter dashboards. Final production tenant-schema routing, schema-level access policy, and legal retention policy.
API enrichment path for filling safe missing values later. Full reporting cube or dashboard-specific aggregate tables.

Source Of Truth Rules

Data category Primary location Rule
Exact original webhook/API payload Restricted encrypted object storage, if raw archive is enabled Do not copy full raw JSON into dashboard-facing tables.
Raw payload archive metadata raw_payload_archive Store pointer, hash, size, source, and retention metadata only.
Real RxNo and RefillNo source_prescription_reference_restricted Store only in the restricted source-reference table because API enrichment may need these values.
Drug attributes drug Canonical events store drug_id only, not repeated drug snapshots.
Payer attributes payer Insurance payers are linked through payment rows. Cash payments use payer_id = null.
Prescription/fill event facts canonical_pharmacy_event Store safe event facts, statuses, dates, quantities, costs, and tokens.
Payment components canonical_event_payer_payment Store insurance, patient pay, cash, and other payment components as rows.

Schema Overview

Full column-level ERD: diagrams/canonical-event-postgres-erd.svg

Tenant schema

The current SaaS design uses one PostgreSQL schema per tenant. All tenant-owned tables live together inside that schema, for example tenant_acme_pharmacy_group. The checked-in SQL uses tenant_template as the local review schema.

Table responsibility groups

Inside each tenant schema, tables are separated by responsibility: tenant/store lookup tables, restricted source-reference tables, audit tables, PHI-minimized canonical event tables, and payment rows. This keeps the model understandable without splitting one tenant's data across multiple logical database schemas.

Main Relationships

Relationship Meaning
tenant to all major tables Every important row is scoped by tenant for multi-pharmacy isolation.
pharmacy to canonical events Each canonical event belongs to a pharmacy when the source data provides or resolves the store.
webhook_event_audit to canonical_pharmacy_event Each canonical event links back to the audit record that explains source, status, duplicate handling, and processing result.
drug to canonical_pharmacy_event Canonical events use drug_id when the drug is available or can be matched.
canonical_pharmacy_event to canonical_event_payer_payment One event may have zero or more payment rows.
canonical_event_payer_payment to payer Insurance payment rows can link to a payer. Cash payment rows intentionally keep payer_id = null.

Processing Flow

  1. Webhook receiver accepts the event and creates an audit record.
  2. Receiver optionally stores raw payload in restricted encrypted storage and stores only archive metadata in the database.
  3. Processor validates the queued event, applies idempotency checks, and updates audit status.
  4. Processor stores real RxNo and RefillNo only in source_prescription_reference_restricted when present.
  5. Processor upserts safe drug and payer lookup rows.
  6. Processor writes one canonical event row and related payment rows.
  7. API enrichment can later use restricted source references to fetch missing details and update only safe fields.

Access Model

Actor or service Allowed access Restriction
Webhook receiver Insert audit rows and raw archive metadata. Do not write canonical rows directly. Do not log raw payloads.
Webhook processor Update audit rows, write restricted references, upsert lookups, and write canonical/payment rows. Do not copy direct patient identifiers into canonical tables or logs.
API enrichment worker Read restricted source references and update safe missing fields in lookup, canonical, and payment tables. Do not expose real RxNo, RefillNo, or raw API responses outside the restricted service boundary.
Dashboard/API application Read safe lookup labels, canonical_pharmacy_event, and canonical_event_payer_payment from the authenticated user's tenant schema and authorized pharmacy scope. No direct access to restricted source-reference tables or raw payload archive.
Database administrator Manage tenant schemas, migrations, indexes, roles, backups, and emergency support. Production access should be limited, named, and audited.

Raw Payload Retention

MVP default: retain restricted raw payload archive records for 30 days. The schema uses retention_until = current_date + 30 for archive metadata rows.

This 30-day value is an MVP engineering default. Before production, legal/security should confirm the retention period and whether deletion should be enforced by S3 lifecycle policy, database cleanup job, or both.

Reviewer Checklist

  • Confirm that the Phase 1 webhook/API fields can map into the current canonical event, drug, payer, and payment tables.
  • Confirm that RxNo and RefillNo being restricted to source_prescription_reference_restricted still supports API enrichment.
  • Confirm that drug details belong in drug and are linked by drug_id, not duplicated in the event row.
  • Confirm that payer details belong in payer and are linked through payment rows.
  • Confirm that cash payment handling is clear: payment_type = 'cash' and payer_id = null.
  • Confirm that dashboard/API users do not need direct access to restricted source-reference tables.
  • Identify any missing fields needed for Phase 1 starter dashboards.
  • Identify any fields that should move from dashboard-facing tables into restricted operational storage.
