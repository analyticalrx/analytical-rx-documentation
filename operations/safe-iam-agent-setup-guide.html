Safe IAM Agent Setup Guide

A controlled way to let an assistant diagnose and apply IAM-only changes for the AnalyticalRx AWS development account.

Purpose

This guide defines how to create a safe IAM-focused agent that can help with access-denied issues, policy reviews, role setup, and permission troubleshooting without giving the agent broad AWS administrator access.

Do not give this agent AdministratorAccess. The agent should not create users, create access keys, change MFA, manage billing, manage organizations, read secrets, or touch production data.

Recommended Model

Decision Recommendation Reason
Account scope Use only in the AWS development account. IAM mistakes are high impact. Keep production/client data out of scope.
Agent identity Prefer an IAM Identity Center permission set assigned only to Bhanu. If not available, use a dedicated IAM user named analytical-rx-iam-agent. A separate identity makes audit logs clear and avoids mixing agent actions with normal human console actions.
Change style Managed policies only. Avoid inline user/group policies. Managed policies are easier to review, version, roll back, and attach consistently.
Resource naming Only manage policies and roles named analytical-rx-* or AnalyticalRx*. Prevents the agent from modifying unrelated AWS account permissions.
Human approval The agent proposes a policy diff first. Bhanu approves before the agent applies the change. IAM changes should be deliberate even in a development account.

What The Agent Can Help With

  • Read an AWS access denied error and identify the missing action, principal, and resource.
  • Inspect current user group policies, role trust policies, and managed policy versions.
  • Generate small IAM policy updates for developer access.
  • Validate IAM policy JSON using IAM Access Analyzer.
  • Create or update AnalyticalRx Lambda execution roles with a permissions boundary.
  • Attach approved AnalyticalRx managed policies to the approved developer group.

What The Agent Must Not Do

  • Do not attach AdministratorAccess or IAMFullAccess.
  • Do not create, delete, or modify IAM users.
  • Do not create, rotate, disable, or delete access keys.
  • Do not change console passwords, MFA devices, or account password policy.
  • Do not manage AWS Organizations, account billing, root access, or service control policies.
  • Do not read application secrets or database credentials.
  • Do not delete roles or managed policies. Leave cleanup to a human administrator.

Setup Overview

  1. Create a permissions boundary for roles that the agent is allowed to create.
  2. Create the IAM agent change policy from the template below.
  3. Create the agent identity or permission set.
  4. Attach the IAM agent change policy to the agent identity.
  5. Configure a local AWS CLI profile named analyticalrx-iam-agent.
  6. Use the agent in proposal-first mode: inspect, propose, validate, apply after approval.

Policy 1: Role Permissions Boundary

Create this customer managed policy first. Name it analytical-rx-role-permissions-boundary. It limits the maximum permissions of roles created by the agent.

{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "AllowWebhookRuntimeBasics",
      "Effect": "Allow",
      "Action": [
        "logs:CreateLogGroup",
        "logs:CreateLogStream",
        "logs:PutLogEvents",
        "sqs:GetQueueAttributes",
        "sqs:GetQueueUrl",
        "sqs:SendMessage",
        "sqs:ReceiveMessage",
        "sqs:DeleteMessage",
        "sqs:ChangeMessageVisibility",
        "kms:Decrypt",
        "secretsmanager:GetSecretValue",
        "xray:PutTraceSegments",
        "xray:PutTelemetryRecords"
      ],
      "Resource": "*"
    }
  ]
}

This boundary does not grant permissions by itself. It only sets a maximum ceiling for roles created by the agent. The actual Lambda execution roles still need attached runtime policies.

Policy 2: IAM Agent Change Policy

Create a customer managed policy named analytical-rx-iam-agent-change-policy. Replace ACCOUNT_ID and DEV_GROUP_NAME before saving.

{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "ReadIamForTroubleshooting",
      "Effect": "Allow",
      "Action": [
        "sts:GetCallerIdentity",
        "iam:Get*",
        "iam:List*",
        "iam:SimulatePrincipalPolicy",
        "iam:SimulateCustomPolicy",
        "iam:GenerateServiceLastAccessedDetails",
        "iam:GetServiceLastAccessedDetails",
        "access-analyzer:ValidatePolicy"
      ],
      "Resource": "*"
    },
    {
      "Sid": "ManageAnalyticalRxManagedPolicies",
      "Effect": "Allow",
      "Action": [
        "iam:CreatePolicy",
        "iam:CreatePolicyVersion",
        "iam:DeletePolicyVersion",
        "iam:SetDefaultPolicyVersion",
        "iam:TagPolicy",
        "iam:UntagPolicy"
      ],
      "Resource": [
        "arn:aws:iam::ACCOUNT_ID:policy/analytical-rx-*",
        "arn:aws:iam::ACCOUNT_ID:policy/AnalyticalRx*"
      ]
    },
    {
      "Sid": "AttachApprovedPoliciesToDevGroup",
      "Effect": "Allow",
      "Action": [
        "iam:AttachGroupPolicy",
        "iam:DetachGroupPolicy"
      ],
      "Resource": "arn:aws:iam::ACCOUNT_ID:group/DEV_GROUP_NAME",
      "Condition": {
        "ArnLike": {
          "iam:PolicyARN": [
            "arn:aws:iam::ACCOUNT_ID:policy/analytical-rx-*",
            "arn:aws:iam::ACCOUNT_ID:policy/AnalyticalRx*"
          ]
        }
      }
    },
    {
      "Sid": "CreateBoundedAnalyticalRxRoles",
      "Effect": "Allow",
      "Action": [
        "iam:CreateRole"
      ],
      "Resource": "arn:aws:iam::ACCOUNT_ID:role/analytical-rx-*",
      "Condition": {
        "StringEquals": {
          "iam:PermissionsBoundary": "arn:aws:iam::ACCOUNT_ID:policy/analytical-rx-role-permissions-boundary"
        }
      }
    },
    {
      "Sid": "ManageAnalyticalRxRoles",
      "Effect": "Allow",
      "Action": [
        "iam:GetRole",
        "iam:UpdateRole",
        "iam:UpdateAssumeRolePolicy",
        "iam:PutRolePermissionsBoundary",
        "iam:TagRole",
        "iam:UntagRole"
      ],
      "Resource": "arn:aws:iam::ACCOUNT_ID:role/analytical-rx-*"
    },
    {
      "Sid": "AttachApprovedPoliciesToAnalyticalRxRoles",
      "Effect": "Allow",
      "Action": [
        "iam:AttachRolePolicy",
        "iam:DetachRolePolicy"
      ],
      "Resource": "arn:aws:iam::ACCOUNT_ID:role/analytical-rx-*",
      "Condition": {
        "ArnLike": {
          "iam:PolicyARN": [
            "arn:aws:iam::ACCOUNT_ID:policy/analytical-rx-*",
            "arn:aws:iam::ACCOUNT_ID:policy/AnalyticalRx*",
            "arn:aws:iam::aws:policy/service-role/AWSLambdaBasicExecutionRole",
            "arn:aws:iam::aws:policy/service-role/AWSLambdaSQSQueueExecutionRole",
            "arn:aws:iam::aws:policy/service-role/AmazonAPIGatewayPushToCloudWatchLogs"
          ]
        }
      }
    },
    {
      "Sid": "DenyDangerousIdentityAndCredentialAdministration",
      "Effect": "Deny",
      "Action": [
        "iam:CreateUser",
        "iam:DeleteUser",
        "iam:UpdateUser",
        "iam:CreateAccessKey",
        "iam:UpdateAccessKey",
        "iam:DeleteAccessKey",
        "iam:CreateLoginProfile",
        "iam:UpdateLoginProfile",
        "iam:DeleteLoginProfile",
        "iam:CreateGroup",
        "iam:DeleteGroup",
        "iam:UpdateGroup",
        "iam:PutGroupPolicy",
        "iam:DeleteGroupPolicy",
        "iam:AttachUserPolicy",
        "iam:DetachUserPolicy",
        "iam:PutUserPolicy",
        "iam:DeleteUserPolicy",
        "iam:EnableMFADevice",
        "iam:DeactivateMFADevice",
        "iam:DeleteVirtualMFADevice",
        "iam:ResyncMFADevice",
        "iam:UpdateAccountPasswordPolicy",
        "iam:DeleteAccountPasswordPolicy",
        "iam:DeleteRole",
        "iam:DeletePolicy",
        "iam:DeleteRolePermissionsBoundary",
        "organizations:*",
        "account:*"
      ],
      "Resource": "*"
    }
  ]
}

Do not put the agent identity in the same developer group it manages. Keep the agent identity separate so it cannot accidentally modify the policies that grant its own access.

Optional Read-Only Mode

For the first few days, use a read-only agent before enabling change mode. Attach AWS managed policy IAMReadOnlyAccess plus this small custom policy:

{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "PolicyAnalysisOnly",
      "Effect": "Allow",
      "Action": [
        "sts:GetCallerIdentity",
        "iam:SimulatePrincipalPolicy",
        "iam:SimulateCustomPolicy",
        "access-analyzer:ValidatePolicy"
      ],
      "Resource": "*"
    }
  ]
}

Read-only mode lets the agent diagnose missing permissions and generate suggested policy JSON, but Bhanu must apply the changes manually.

Known Limitation

The change policy restricts which IAM policies and roles the agent can edit by name and ARN. It does not prove that every new policy document is business-safe. For example, an agent with policy update access could technically create a broad policy version under an approved policy name unless the human approval workflow catches it.

Use read-only mode if you want the strongest safety. In read-only mode, the agent can inspect AWS and write the policy JSON for you, but only Bhanu can paste and apply the change in the AWS console.

Use change mode only in the development account, only with explicit approval, and only after reviewing IAM Access Analyzer findings.

Local AWS CLI Profile

Configure the agent profile locally. Do not paste access keys into chat or documentation.

aws configure --profile analyticalrx-iam-agent

Use the profile only when doing IAM support work:

export AWS_PROFILE=analyticalrx-iam-agent
export AWS_REGION=us-east-1
aws sts get-caller-identity

If using IAM Identity Center instead of long-lived access keys, configure the profile with AWS SSO and sign in before use.

Agent Operating Rules

  1. Confirm identity with aws sts get-caller-identity.
  2. Inspect the current principal, group, role, and policy versions.
  3. Identify the exact missing action and target resource from the access denied message.
  4. Propose the smallest policy diff that fixes the issue.
  5. Validate the proposed policy with IAM Access Analyzer.
  6. Show Bhanu the diff and validation result.
  7. Apply only after explicit approval.
  8. After applying, re-run the failing operation or IAM simulation if possible.
  9. Record the changed policy name, version, and reason in the final response.

Useful Commands

Command Purpose
aws sts get-caller-identity Confirms the agent is using the intended AWS identity.
aws iam list-attached-group-policies --group-name DEV_GROUP_NAME Lists policies currently attached to the developer group.
aws iam get-policy-version --policy-arn POLICY_ARN --version-id VERSION_ID Reads the exact JSON for a managed policy version before editing.
aws accessanalyzer validate-policy --policy-document file://policy.json --policy-type IDENTITY_POLICY Runs IAM Access Analyzer checks before saving a policy.
aws iam simulate-principal-policy --policy-source-arn PRINCIPAL_ARN --action-names ACTION_NAME Checks whether a principal is allowed to call a specific AWS action.

Approval Checklist

Before approving an IAM change from the agent, confirm:

  • The change is for the development account only.
  • The policy name starts with analytical-rx- or AnalyticalRx.
  • The change does not add Action: "*" or iam:*.
  • The change does not attach AdministratorAccess, IAMFullAccess, or billing/organization permissions.
  • The change does not allow credential administration such as access key creation or MFA changes.
  • The policy passed IAM Access Analyzer validation or the remaining findings were reviewed intentionally.
  • The agent has shown what it will change before applying it.

Audit And Rollback

  • Use managed policy versions so changes can be rolled back by setting the previous version as default.
  • Keep CloudTrail enabled for IAM management events so policy and role changes are auditable.
  • When the AWS limit of managed policy versions is reached, delete only an old non-default version after human approval.
  • Review the agent identity monthly and remove it when the team no longer needs IAM assistance.

Example Request To The Agent

My teammate is getting AccessDenied for iam:GetAccountSummary.
Use the analyticalrx-iam-agent profile.
Inspect the current dev group policies, propose the smallest policy change,
validate it with IAM Access Analyzer, and wait for my approval before applying.
